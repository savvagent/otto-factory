# Console internationalization — English, Spanish, German, French, Italian, Hindi

## Goal

Every string a human reads in a browser — the SvelteKit console and the two server-rendered
pages in `df-web` — available in six languages, with a gate that makes a partial translation
unmergeable.

## Status — 2026-09-05

🚧 In progress. Implements [`#42`](https://github.com/savvagent/dark-factory/issues/42).

Tasks 1–8 and 14 landed. 9–13 in flight.

**Spec:** `docs/specs/2026-09-05-console-i18n-design.md` — read it first. This plan implements it
exactly.

## Global Constraints

- `web/` conventions: Svelte 5 runes only (`$state`/`$derived`/`$props`/`$effect`), no `export let`,
  no Svelte 4 stores, Tailwind v4, `adapter-static` (**no SvelteKit server may be introduced** —
  see `web/README.md` on why the SPA is a security decision).
- **Every SQL statement lives in `df-core`.** A query in `df-web` is a bug.
- `users` is **not** a tenant table — no `org_id`, absent from `tenant_tables` in `0007_rls.sql`
  (verified). The two-guard rule and the cross-org negative test do **not** apply to
  `users.locale`. Say so in the task rather than skipping it silently.
- Migrations are forward-only. Never edit an applied migration.
- The MCP surface stays English — `df-mcp` tool descriptions and `df-core` error messages are
  written for an LLM caller (CLAUDE.md, "Descriptions are the documentation").
- No AI self-attribution anywhere (commits, comments, docs, PR body).
- Gates, all of which must pass before the PR opens:
  `cd web && npm run check && npm run lint && npm test && npm run build`;
  `cargo test && cargo clippy --all-targets -- -D warnings && cargo fmt --all --check`.
- Commit format is the repo's: `<area>: <subject>` — e.g. `web: extract org route strings`,
  `df-core: add users.locale`. Not conventional-commits types.
- Postgres must be up for `cargo test`: `podman compose up -d` (host port 15433), `.env` from
  `.env.example`.

## Task Order & Rationale

Server before console, because the console's locale runtime reads `me.user.locale` and there is
no point building the client against a field that does not exist. Within the console: runtime
(6–7) before extraction (8–10), because every extracted string needs somewhere to resolve from;
extraction before translation (12), because translating a moving target is wasted work;
translation before the expansion audit (13), because German is what breaks the layout and it has
to exist first.

Tasks 1–5 and 6–11 are each independently mergeable in principle; they land together because the
issue asks for one PR.

## Task 1 — Paraglide toolchain and the completeness gate

**Files:** `web/package.json`, `web/project.inlang/settings.json`, `web/messages/*.json`,
`web/scripts/check-messages.mjs`, `web/scripts/check-messages.test.ts`, `web/vite.config.ts`,
`web/.prettierignore`, `.gitignore`

**Interfaces:** produces `$lib/paraglide/messages` (`m.*`) and `$lib/paraglide/runtime`
(`locales`, `overwriteGetLocale`). Consumed by every later console task.

**Already verified empirically against `@inlang/paraglide-js@2.25.0` — do not re-litigate:**

- The ICU one-liner `"{count, plural, one {# job} other {# jobs}}"` **does not work**; it compiles
  to the literal `undefined other }`. Use the variant form:
  ```json
  { "key": [{ "declarations": ["input count", "local countPlural = count: plural"],
              "selectors": ["countPlural"],
              "match": { "countPlural=one": "# job", "countPlural=other": "# jobs" } }] }
  ```
- `--emit-ts-declarations` is **required**. Without it no `.d.ts` is emitted and an unknown key
  type-checks clean; with it, `m.nope()` is `TS2339`. This is what satisfies the issue's
  "message keys must be type-checked".
- A key missing from a non-base catalog **silently returns the English string**. This is why
  `check-messages.mjs` exists.
- `es`/`fr`/`it` need the `many` plural category; `en`/`de`/`hi` do not.

- [ ] `npm i -D @inlang/paraglide-js@^2.25.0` (devDependency — it is a compiler, not a runtime).
- [ ] `project.inlang/settings.json`: `baseLocale: "en"`, `locales: ["en","es","de","fr","it","hi"]`,
      `plugin.inlang.messageFormat.pathPattern: "./messages/{locale}.json"`.
- [ ] `vite.config.ts`: add `paraglideVitePlugin({ project: './project.inlang', outdir:
      './src/lib/paraglide', emitTsDeclarations: true })` to `plugins`, **before** `sveltekit()`.
- [ ] `package.json` scripts: add
      `"paraglide:compile": "paraglide-js compile --project ./project.inlang --outdir ./src/lib/paraglide --emit-ts-declarations"`;
      prepend it to `check` and `build`; add `node scripts/check-messages.mjs` to `check`.
      `check` becomes: `npm run paraglide:compile && node scripts/check-messages.mjs && svelte-kit sync && svelte-check … && npm run check:worker`.
- [ ] `.gitignore`: `web/src/lib/paraglide`. `web/.prettierignore`: `src/lib/paraglide`.
- [ ] Seed `messages/en.json` with the handful of keys Task 6/7 will need first, and give the
      other five real translations for those same keys — the gate must pass from this commit on.
- [ ] `scripts/check-messages.test.ts`: import `check()` and assert it flags each of — missing key,
      extra key, dropped placeholder, missing plural category, stray plural category, shape
      mismatch — and passes a correct set. (The script is written and these six cases are already
      confirmed to fire; the test pins them.)
- [ ] Gates: `npm run check`, `npm run lint`, `npm test`, `npm run build`.
- [ ] Commit: `web: add paraglide toolchain and message completeness gate`.

## Task 2 — `df-core::i18n` and the `users.locale` column

**Files:** `crates/df-core/src/i18n.rs` (new), `crates/df-core/src/lib.rs`,
`crates/df-core/migrations/0018_user_locale.sql` (new), `crates/df-core/src/orgs.rs`

**Interfaces:** `df_core::i18n::{Locale, SUPPORTED_LOCALES}` — **the one hand-written locale list
in Rust**. `User.locale: Option<String>`. `Db::set_profile` gains a tri-state locale parameter.

- [ ] `i18n.rs`: `Locale` enum (`En, Es, De, Fr, It, Hi`) with `as_str()`, `FromStr`, `Default = En`;
      `SUPPORTED_LOCALES: [&str; 6]`. Doc comment says this is the owner and names the three
      places that mirror it.
- [ ] Test in `i18n.rs`: read `web/project.inlang/settings.json` and assert its `locales` array
      equals `SUPPORTED_LOCALES`. **`CARGO_MANIFEST_DIR` is the crate directory** — the path is
      `concat!(env!("CARGO_MANIFEST_DIR"), "/../../web/project.inlang/settings.json")`. This is the
      drift guard; without it the picker can offer a locale the server rejects.
- [ ] `0018_user_locale.sql`: `ALTER TABLE users ADD COLUMN locale text;` — nullable, **no default,
      no backfill**. `NULL` means "never chose", which is not the same as "chose English". Comment
      says why there is no `CHECK` (a seventh locale would become a migration; `df-core` validates).
- [ ] `orgs.rs`: add `locale: Option<String>` to `User`; add `locale` to `USER_COLS`.
- [ ] `set_profile` gains `locale: Option<Option<&str>>`: `None` leaves it alone, `Some(None)`
      clears it to `NULL`, `Some(Some(l))` validates against `SUPPORTED_LOCALES` and sets it.
      Invalid → `Error::Invalid` **naming the six valid options** (house error style).
      SQL: `locale = CASE WHEN $4 THEN $5 ELSE locale END` (a bool "touch it" flag plus the value)
      — `COALESCE` cannot express "set to NULL".
- [ ] `#[sqlx::test]`s in `df-core`: round trip set/clear/leave-alone; invalid locale rejected with
      a message naming the options. **No cross-org test — `users` has no `org_id` and is not a
      tenant table.** State that in a comment on the test module.
- [ ] Gates: `cargo test -p df-core`, `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all`.
- [ ] Commit: `df-core: add users.locale and the supported-locale list`.

## Task 4 — `df-web::i18n`: negotiation and the page message table

**Files:** `crates/df-web/src/i18n.rs` (new), `crates/df-web/src/lib.rs`

**Interfaces:** `negotiate(Option<&str>) -> Locale`; `msg(Locale, Key) -> &'static str`.
`pub use df_core::i18n::Locale` — `df-core` cannot depend on `df-web`, so the enum lives there and
this crate re-exports it.

- [ ] `negotiate`: RFC 9110 `Accept-Language`. Split on `,`; parse `;q=` (default `1.0`); **drop
      `q=0` entries entirely** (that means "not acceptable", not "rank last"); match on the primary
      subtag so `es-419` → `es`; sort by descending weight, stable; first supported wins; else `En`.
      Malformed entries are skipped, never fatal. `*` alone → `En`.
- [ ] `Key` enum + `msg(locale, key)` — an exhaustive `match` on both, so a new key without a
      translation **fails to compile** rather than rendering blank.
- [ ] Unit tests: the worked examples from RFC 9110, plus `q=0`, malformed input, empty, absent,
      `*`, region subtags, and an unsupported language falling through to a supported one later in
      the list.
- [ ] Gates: `cargo test -p df-web`, clippy, fmt.
- [ ] Commit: `df-web: negotiate Accept-Language for the browser-facing pages`.

## Task 7 — `errors.ts`, `WebauthnError` codes, and `api.ts`'s own messages

**Files:** `web/src/lib/errors.ts` (new), `web/src/lib/webauthn.ts`, `web/src/lib/api.ts`

**Interfaces:** `messageFor(e: ApiError | WebauthnError): string`.

- [ ] `WebauthnError` gains a `code`, so it goes through the same door as `ApiError` — the house
      rule is "an error has a code before it has a message", and this is the one error type that
      was exempt. Codes for the six throw sites: `no_passkey_created`, `no_passkey_offered`,
      `cancelled`, `already_registered`, `unsupported`, `browser_refused` (carries `{name}`).
      Keep the English message as the constructor's second argument — it is the fallback.
- [ ] `api.ts`: the two client-authored messages keep their codes (`network`, `unknown`) and get
      keyed messages. Every other `ApiError` message still comes from the server.
- [ ] `errors.ts`: map the codes `df-web` can actually return — enumerated from
      `df_core::Error::code()`, `df-web`'s `auth_code()`, and `df-billing`'s quota code. **Unknown
      code → render `e.message`.**
- [ ] **Rewrite the three catch blocks that render these** — `login/+page.svelte:44`,
      `signup/+page.svelte:52`, `settings/+page.svelte:66`. Each is currently
      `e instanceof WebauthnError || e instanceof ApiError ? e.message : '<English literal>'`.
      Call `messageFor(e)` instead, **and key each `else` literal** (`'Could not load your
      passkeys.'`, `'That did not work.'`, `'Could not save that.'`). **This is the load-bearing
      half** — adding a `code` field and stopping there leaves the login page's entire error
      surface in English.
- [ ] Vitest: a fabricated unknown code renders the thrower's message and is non-empty. **The issue
      names this test explicitly.**
- [ ] Gates: `npm run check`, `npm run lint`, `npm test`.
- [ ] Commit: `web: key error messages by code, with the English message as fallback`.
